## 要解决的问题

前几篇的节点都是「正经组件」：ChatModel、ToolsNode、Retriever……它们要实现接口、要声明 Option 类型。但图里大量逻辑是**一次性的胶水**：

- 把模型输出的 `*schema.Message` 包成 `[]*schema.Message` 喂给下一个节点；
- 把一个字符串改一改、抽个字段、拼个 prompt；
- 写个自定义解析器、打个日志副作用。

为这些写一个完整组件太重了。eino 提供 **Lambda**：一个普通 Go 函数就是一个节点。它和组件一样能 `AddLambdaNode` / `AppendLambda`，一样支持流式、能被 fan-in/fan-out、能挂 callback。本篇看 Lambda 怎么用最小的表面（一个函数）接入整套 Runnable 体系。

## 四种函数类型

Lambda 对应第 02 篇讲的四种数据流范式，定义了四个函数类型（`compose/types_lambda.go`）：

{% highlight go %}
type Invoke[I, O, TOption any] func(ctx context.Context, input I, opts ...TOption) (output O, err error)

type Stream[I, O, TOption any] func(ctx context.Context,
    input I, opts ...TOption) (output *schema.StreamReader[O], err error)

type Collect[I, O, TOption any] func(ctx context.Context,
    input *schema.StreamReader[I], opts ...TOption) (output O, err error)

type Transform[I, O, TOption any] func(ctx context.Context,
    input *schema.StreamReader[I], opts ...TOption) (output *schema.StreamReader[O], err error)
{% endhighlight %}

三个泛型参数：输入 `I`、输出 `O`、option 类型 `TOption`。绝大多数胶水函数不需要 option，eino 另外给了四个「无 option」版本（`InvokeWOOpt` 等，签名里没有 `opts ...`），以及对应的便捷构造器。

## 构造器：你只写一种，其余自动补

用户通常只关心一种范式。比如我就想写个「值进值出」的函数，用 `InvokableLambda`：

{% highlight go %}
lambda := compose.InvokableLambda(func(ctx context.Context, input string) (string, error) {
    return strings.ToUpper(input), nil
})
{% endhighlight %}

它内部把无 option 的函数适配成带 option 的形式，然后交给 `anyLambda`：

{% highlight go %}
func InvokableLambda[I, O any](i InvokeWOOpt[I, O], opts ...LambdaOpt) *Lambda {
    f := func(ctx context.Context, input I, opts_ ...unreachableOption) (output O, err error) {
        return i(ctx, input)
    }
    return anyLambda(f, nil, nil, nil, opts...)
}
{% endhighlight %}

`unreachableOption` 是个空标记类型，表示「这个 Lambda 不接收 option」。同理还有 `StreamableLambda`、`CollectableLambda`、`TransformableLambda`，分别只传 `s`/`c`/`t`。

如果你一个函数想同时提供多种范式的高效实现（而不是让框架用降级转换凑），用 `AnyLambda` 显式传四个（任意为 nil）：

{% highlight go %}
func AnyLambda[I, O, TOption any](i Invoke[I, O, TOption], s Stream[I, O, TOption],
    c Collect[I, O, TOption], t Transform[I, O, TOption], opts ...LambdaOpt) (*Lambda, error) {

    if i == nil && s == nil && c == nil && t == nil {
        return nil, fmt.Errorf("needs to have at least one of four lambda types: invoke/stream/collect/transform, got none")
    }
    return anyLambda(i, s, c, t, opts...), nil
}
{% endhighlight %}

唯一的硬性校验：四个不能全是 nil，否则这个 Lambda 啥也干不了。

## anyLambda：复用 runnablePacker

`anyLambda` 是关键——它**没有为 Lambda 另写一套执行逻辑**，而是调第 02 篇见过的 `runnableLambda` → `newRunnablePacker`：

{% highlight go %}
func anyLambda[I, O, TOption any](i Invoke[...], s Stream[...], c Collect[...], t Transform[...], opts ...LambdaOpt) *Lambda {
    opt := getLambdaOpt(opts...)

    executor := runnableLambda(i, s, c, t, !opt.enableComponentCallback)
    executor.meta = &executorMeta{
        component:                  ComponentOfLambda,
        isComponentCallbackEnabled: opt.enableComponentCallback,
        componentImplType:          opt.componentImplType,
    }
    return &Lambda{executor: executor}
}
{% endhighlight %}

回想第 02 篇的 `newRunnablePacker`：你只给了 `Invoke`，它会自动用 `streamByInvoke`（把输出包成单元素流）、`collectByInvoke`（concat 输入再 invoke）、`transformByInvoke`（concat 输入、invoke、再包成流）补齐另外三个。于是**一个「值进值出」的 Lambda，放进流式图里也能正常工作**——框架在边界自动做流和值的转换。反过来你只给 `Stream`，框架用 `invokeByStream`（ drain 流再 concat）补出 `Invoke`。

这就是 Lambda「写一个函数就行」的底层秘密：**四模式的补齐是 Runnable 层的通用能力，Lambda 只是最薄的一个入口**。组件（ChatModel 等）走的也是同一个 packer。

`Lambda` 结构体本身就一个字段：

{% highlight go %}
type Lambda struct {
    executor *composableRunnable
}
{% endhighlight %}

它持有的 `composableRunnable` 和编译后的图、和组件包装出来的东西是同一个类型。所以图在编译时看到一个 Lambda 节点，和看到一个 ChatModel 节点没有结构差别——这再次落到「一切皆 composableRunnable」。

## 类型怎么来：泛型推断

Lambda 没有手写 `inputType()`/`outputType()`，类型从哪来？在 `toComposableRunnable` 里用泛型拿：

{% highlight go %}
inputType := generic.TypeOf[I]()
outputType := generic.TypeOf[O]()
optionType := generic.TypeOf[TOption]()
c := &composableRunnable{
    genericHelper: newGenericHelper[I, O](),
    inputType:     inputType,
    outputType:    outputType,
    optionType:    optionType,
}
{% endhighlight %}

`generic.TypeOf[I]()` 就是 `reflect.TypeOf((*I)(nil)).Elem()` 的封装。于是你写 `InvokableLambda(func(ctx, in string)(*schema.Message,error))`，编译器从函数字面量推断出 `I=string`、`O=*schema.Message`，Lambda 的输入输出类型自动确定，建图期的类型检查（第 03 篇 `checkAssignable`）据此判断这条边连不连得上。**类型信息在编译期由泛型锁定，运行时用反射读取**，用户无需手写。

## 两个内置 Lambda

eino 附带两个常用胶水 Lambda：

**ToList**——把单个输入包成单元素切片，常用于「模型输出 `*schema.Message`，下一节点要 `[]*schema.Message`」：

{% highlight go %}
func ToList[I any](opts ...LambdaOpt) *Lambda {
    i := func(ctx context.Context, input I, opts_ ...unreachableOption) ([]I, error) {
        return []I{input}, nil
    }
    f := func(ctx context.Context, inputS *schema.StreamReader[I], opts_ ...unreachableOption) (*schema.StreamReader[[]I], error) {
        return schema.StreamReaderWithConvert(inputS, func(i I) ([]I, error) {
            return []I{i}, nil
        }), nil
    }
    return anyLambda(i, nil, nil, f, opts...)   // 同时给了 Invoke 和 Transform
}
{% endhighlight %}

注意它特意同时提供了 `Invoke`（值）和 `Transform`（流）：流式下用 `StreamReaderWithConvert` 把每个 chunk 包成 `[]I`，避免「先把整条流 concat 成一个值再包切片」的缓冲——这是个「手写高效范式而非依赖降级」的范例。

**MessageParser**——把 `*schema.Message` 解析成结构体 T，接在模型后面：

{% highlight go %}
func MessageParser[T any](p schema.MessageParser[T], opts ...LambdaOpt) *Lambda {
    i := func(ctx context.Context, input *schema.Message, opts_ ...unreachableOption) (output T, err error) {
        return p.Parse(ctx, input)
    }
    opts = append([]LambdaOpt{WithLambdaType("MessageParse")}, opts...)
    return anyLambda(i, nil, nil, nil, opts...)
}
{% endhighlight %}

`WithLambdaType` 给它一个可读的实现类型名（进 callback 的 `RunInfo.Type`），trace 里能看到 "MessageParse" 而不是反射出来的匿名函数名。

## 设计取舍

- **函数即节点，零仪式**：不用定义结构体、不用实现完整接口，一个函数字面量就能进图。泛型同时锁定输入输出类型，类型安全不打折。
- **复用 Runnable 降级层而非特判**：Lambda 不自己处理流式/非流式转换，全交给 `newRunnablePacker`。这让 Lambda 的代码量极小，也保证它和组件行为完全一致。
- **默认无 option，需要时再上 AnyLambda**：`unreachableOption` 让 90% 的胶水函数用最简单的签名；真要传 option 或手写高效流式，`AnyLambda` 提供逃生门。
- **callback 默认由框架包一层**：`!enableComponentCallback` 意味着 Lambda 默认让框架在外面套 callback 切面（因为用户函数内部不会自己触发）；高级用户可以 `WithLambdaCallbackEnable` 表示函数内部自己处理。
- **ToList/MessageParser 示范「该手写流式就手写」**：虽然降级能凑出正确结果，但对流式热点路径，直接给 `Transform` 实现能省掉 concat 缓冲，降低首 token 延迟。

## 自己动手

- [ ] 用 `InvokableLambda` 写一个 `string → string` 的函数，加进 Chain，分别用 `Invoke` 和 `Stream` 调用，验证你只写了 Invoke，Stream 也能跑通（框架自动降级）。
- [ ] 故意 `AnyLambda(nil,nil,nil,nil)`，观察 `needs to have at least one of four lambda types` 报错。
