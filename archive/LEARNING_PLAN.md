# 工业界 LLM 知识规划

## 定位

这是一张面向资深分布式系统架构师的工业界知识地图，不是论文目录，也不是某个框架的使用教程。目标是形成端到端判断力：面对一个 LLM 业务，能够判断模型、数据、检索、系统、平台、治理和商业约束分别应该承担什么责任，并能做出可落地的架构与成本决策。

工业界的核心问题不是“模型能不能生成”，而是：

- 质量是否可度量、可回归、可解释；
- 延迟、吞吐、成本和可靠性是否满足业务 SLO；
- 数据、模型、提示词和工具是否能够持续迭代；
- 系统是否安全、合规、可审计、可回滚；
- 方案是否能在组织和商业约束下长期运营。

## 知识分层

每个领域按三层掌握，避免把时间平均分配给所有细节：

- **L1：架构判断**：能识别问题、比较方案、估算代价、发现风险。
- **L2：系统实现**：能读关键源码、设计接口、搭建实验、定位瓶颈。
- **L3：算法细节**：只在确实影响产品指标或平台决策时深入推导和复现。

你的重点应是所有领域的 L1，推理/训练/数据/评测/平台的 L2，以及与当前业务直接相关方向的 L3。

## 一、模型与能力边界

### 必须掌握

- Transformer decoder、tokenization、attention、RoPE、RMSNorm、SwiGLU、logits。
- causal LM、上下文窗口、KV Cache、prefill/decode。
- Base Model、Instruction Model、Reasoning Model 的能力边界。
- 参数量、FLOPs、激活显存、权重显存和上下文长度的粗略估算。
- 模型选择的关键维度：质量、中文能力、上下文、工具调用、多模态、许可证、价格和生态。

### 需要理解

- Scaling Law、MoE、GQA/MQA、长上下文、推理时计算。
- 预训练、继续预训练、SFT、DPO、蒸馏和量化分别解决什么问题。
- 为什么 benchmark 分数不能直接等价于业务效果。

### 工业产出

建立一份模型选型矩阵，并为一个业务场景写出模型能力边界、失败模式和替代方案。

## 二、数据与知识资产

### 必须掌握

- 数据生命周期：采集、清洗、去重、切分、标注、版本、发布、下线。
- 训练数据、偏好数据、评测数据、知识库数据和线上反馈的区别。
- 文档解析、chunking、metadata、权限、数据血缘和增量更新。
- 数据质量、污染、时效性、覆盖率、隐私和版权。

### 需要理解

- 数据混合比例、token budget、packing、合成数据和数据飞轮。
- 知识库的倒排、向量、混合检索、rerank 和 query rewrite。
- 数据闭环为什么通常比更换模型更能决定长期效果。

### 工业产出

设计一个带版本、权限、血缘、质量门禁和回滚能力的数据/知识平台。

## 三、训练与模型适配

### 必须掌握

- 什么时候使用 Prompt、RAG、SFT、LoRA、DPO、继续预训练或换模型。
- 训练任务的资源、数据、checkpoint、实验追踪和模型注册。
- 数据并行、张量并行、流水线并行、ZeRO/FSDP 的适用场景。
- 混合精度、梯度累积、checkpoint、容错、恢复和版本管理。

### 需要理解

- 训练吞吐、通信占比、GPU 利用率、有效 token 成本。
- 训练平台的队列、公平性、抢占、弹性扩缩和多租户隔离。
- 线上反馈如何进入数据筛选、训练、评测和灰度闭环。

### 工业产出

写出一份模型适配决策树和训练平台架构，明确数据、实验、模型、发布之间的可追溯关系。

## 四、推理与模型服务

### 必须掌握

- continuous batching、调度、流式输出、请求取消、优先级和限流。
- TTFT、TPOT、E2E latency、吞吐、队列等待和 GPU 利用率。
- KV Cache、paged attention、prefix caching、量化、speculative decoding。
- 单机、多卡、多节点、模型副本、模型路由和故障转移。

### 需要理解

- prefill/decode 分离、PD disaggregation 和通信代价。
- vLLM、TensorRT-LLM、SGLang 等推理引擎的定位与边界。
- 大模型服务的容量模型：上下文分布、输出长度、并发、峰值和故障余量。

### 工业产出

构建一份推理服务标准：接口、SLO、容量、成本、降级、灰度、回滚和多租户策略。

## 五、LLM 应用架构

### 必须掌握

- RAG、工具调用、结构化输出、工作流、Agent 的边界。
- Context Engineering：上下文选择、压缩、记忆、状态和提示词版本。
- 确定性 workflow、单 Agent 和多 Agent 的选型原则。
- 幂等、重试、超时、人工介入、沙箱、审计和权限。

### 需要理解

- Agent 的状态机、事件模型、任务恢复和长任务调度。
- 工具调用的 schema、版本兼容、结果校验和副作用控制。
- 为什么很多 Agent 问题应通过工作流、数据或产品约束解决。

### 工业产出

设计一个企业级 LLM 应用平台，包含应用编排、工具中心、上下文服务、状态存储和人工审核。

## 六、评测、可观测性与质量工程

### 必须掌握

- 离线评测、在线评测、人工评测和线上反馈的分工。
- 任务成功率、准确性、groundedness、幻觉、拒答、工具正确性和成本。
- Golden Set、回归集、对抗集、抽样、标注一致性和评测门禁。
- Trace、prompt、检索结果、工具调用、模型版本和最终回答的关联。

### 需要理解

- LLM-as-a-Judge 的偏差、校准和人工抽检。
- 质量与延迟、成本、安全之间的多目标优化。
- 如何定位问题属于检索、上下文、模型、提示词、工具还是业务流程。

### 工业产出

建立一套从请求到答案的质量工程体系：指标字典、评测集、trace schema、回归门禁和故障分级。

## 七、平台工程与生产可靠性

### 必须掌握

- 模型网关、路由、配额、鉴权、租户隔离、密钥和成本归属。
- 模型/提示词/数据集/评测集/索引/工具的版本管理。
- 灰度、A/B、回滚、熔断、降级、限流、缓存和灾备。
- GPU 资源池、调度、可观测性、容量规划和成本分摊。

### 需要理解

- LLM 平台与传统微服务平台的相同点和不同点。
- 长连接、流式响应、异步任务、队列和最终一致性。
- 供应商 API、开源模型、自建模型和混合部署的架构取舍。

### 工业产出

写出 LLM Platform as a Service 的参考架构和服务目录，服务目录至少包含模型服务、评测服务、知识服务、工具服务和观测服务。

## 八、安全、合规与治理

### 必须掌握

- Prompt Injection、数据泄露、越权检索、工具滥用、供应链和不安全输出。
- 输入/输出安全、敏感信息处理、权限传播、租户隔离和审计。
- 模型、数据、提示词、工具和知识库的责任边界。
- 内容安全、版权、隐私、数据驻留和监管要求。

### 需要理解

- 红队测试、攻击面建模、风险分级和上线门禁。
- 安全策略对召回、可用性、成本和用户体验的影响。
- 高风险场景中的人工复核、可解释性和证据链。

### 工业产出

完成一份 LLM 威胁模型、数据分级规范、权限模型和上线检查清单。

## 九、商业与组织能力

### 必须掌握

- 单位请求成本、单位任务成本、毛利、峰值资源和供应商锁定。
- Build/Buy、API/自建、通用模型/垂直模型、质量/成本/时延的取舍。
- LLM 能力如何嵌入业务流程，而不是只做聊天入口。
- 平台团队、模型团队、数据团队、应用团队和安全团队的边界。

### 需要理解

- 模型能力迭代对产品、运营、客服和组织流程的影响。
- 试验项目如何转为稳定服务：指标、负责人、预算、SLO 和退出条件。

### 工业产出

为一个真实业务写出立项方案：用户价值、成功指标、成本模型、风险、组织依赖和 90 天路线图。

## 学习顺序与节奏

建议按三轮推进，而不是平均学习所有知识。

### 第一轮：建立全局地图（4 周）

模型与能力边界 → 数据与 RAG → 推理与服务 → 评测与治理。目标是能够参加 LLM 方案评审并提出关键问题。

### 第二轮：补齐系统深度（6-8 周）

训练系统 → 推理引擎 → Agent Runtime → 平台工程。目标是能够读源码、做 benchmark、算容量并设计生产系统。

### 第三轮：绑定一个业务场景（持续）

选择客服、搜索、研发助手、运营分析或企业知识库中的一个场景，完整走通数据、模型、应用、评测、上线和运营。

每周时间建议：30% 读论文和源码，40% 做实验和 benchmark，20% 写架构/ADR，10% 做复盘和分享。每两周进行一次架构评审，要求用数据而不是观点支撑结论。

### 长期资源导航（14 天之后，非进度）

以下是完成 14 天正式计划后的按需深入顺序，不是第二套课程周期，不计入页面进度，也没有每日完成要求。

#### 阶段 A：建立必要直觉和共同语言

- **主线**：3Blue1Brown → 吴恩达/StatQuest 按需补数学和 ML 概念。
- **主题**：向量、矩阵、梯度、概率、交叉熵、过拟合、评估指标。
- **跳过规则**：线性代数和分布式系统基础不做系统刷题，只补能解释 LLM 计算图的部分。
- **产出**：一页“LLM 计算图与资源估算”笔记；能解释参数量、FLOPs、显存、token 和 loss 的关系。

#### 阶段 B：跟 Karpathy 从零实现模型

- **主线**：Andrej Karpathy 的 Neural Networks: Zero to Hero。
- **顺序**：micrograd → makemore → GPT/tokenizer/attention → nanoGPT 类训练流程。
- **配套**：遇到概念障碍看 3Blue1Brown；遇到概率和评估问题看 StatQuest。
- **架构师视角**：不追求手写出生产模型，重点观察计算图、内存、batch、序列长度、训练吞吐和 checkpoint。
- **产出**：一个可运行的小型 decoder-only Transformer；一份从单机训练到服务化的差距清单。

#### 阶段 C：用吴恩达和李宏毅形成体系

- **主线**：吴恩达的机器学习/深度学习体系 + 李宏毅的 Transformer、生成式 AI、LLM 相关课程。
- **主题**：训练目标、优化、数据中心 AI、SFT、RLHF/DPO、prompt、RAG、Agent。
- **学习方法**：每个主题只回答三个问题：解决什么问题？边界是什么？生产系统的指标是什么？
- **产出**：Prompt/RAG/SFT/DPO/换模型的决策树；一个业务场景的模型适配 ADR。

#### 阶段 D：跟 AssemblyAI 做应用工程

- **主线**：AssemblyAI 的 NLP/LLM 工程教程和示例。
- **主题**：embedding、RAG、chunking、reranking、结构化输出、评测、语音/多模态（若业务需要）。
- **改造要求**：每个示例补齐租户隔离、权限过滤、超时重试、trace、成本统计和离线评测。
- **产出**：一个可运行的 RAG 或 LLM 应用服务；包含 golden set、recall@k、groundedness、延迟和单请求成本。

#### 阶段 E：跟 Yannic Kilcher 精读关键论文

- **主线**：Yannic Kilcher 的论文解读，原论文必须作为最终依据。
- **建议主题**：Transformer、Scaling Law、FlashAttention、ZeRO、LoRA、DPO、RAG、speculative decoding、MoE。
- **观看方法**：先看解读形成问题，再读论文摘要、方法、实验、限制，最后看源码或复现实验。
- **产出**：至少 5 篇论文卡片，每张包含问题、核心机制、收益、代价、实验、工业适用边界。

#### 阶段 F：用 Two Minute Papers 建立趋势雷达

- **主线**：每周扫描 Two Minute Papers，选择与当前业务或平台相关的 3 个主题深入验证。
- **主题**：推理优化、长上下文、多模态、Agent、合成数据、模型压缩等。
- **约束**：视频只负责发现，不负责证明；不因 demo 或标题改变生产架构。
- **产出**：一份技术雷达，分为“立即实验、持续观察、暂不采用”，每项写出采用条件。

#### 阶段 G：综合输出

- **主线**：回看 Karpathy 的实现，结合吴恩达/李宏毅的体系、AssemblyAI 的应用、Yannic 的论文和 Two Minute Papers 的趋势。
- **任务**：为一个真实业务完成端到端方案：数据 → 模型 → RAG/工具 → 推理 → 评测 → 安全 → 运营。
- **产出**：架构设计、benchmark、容量和成本模型、故障演练、灰度/回滚方案、90 天路线图。

### 可选的长期观看与实践节奏

- **周一**：看一节主线课程，写下 3 个需要验证的问题。
- **周二**：看配套直觉视频或中文讲解，补齐概念。
- **周三**：读代码或论文，定位到关键模块/公式/实验。
- **周四**：做实验或改造示例，记录延迟、吞吐、显存、质量和成本。
- **周五**：写 ADR 或论文卡片，回答“是否值得进入生产”。
- **周末**：用 Two Minute Papers 做趋势扫描，并整理下周要验证的一个主题。

### 观看完成标准

以下情况才算学完一个主题：

- 能不用视频原话解释核心机制；
- 能指出它解决的系统瓶颈和引入的代价；
- 能运行或阅读一个最小实现；
- 能设计一个可复现实验；
- 能说明它在生产系统中的适用边界。

官方入口建议：Karpathy 的 Zero to Hero 课程页面 karpathy.ai/zero-to-hero.html；其余创作者优先从本人频道、课程主页和对应 GitHub 仓库进入。不要依赖二次搬运或只看摘要。

## 14 天正式计划：Day 1–7

本期是每天 90–120 分钟的高密度架构师路线，不是把长期学习目录机械压缩。以下四天形成第一条可验收因果链：先定义业务问题，再理解模型机制，用最小实现验证理解，最后把输入建设成可追溯数据资产。页面与本节采用相同的主题、时长、产出和验收口径；只有提交回答、外部产出证据声明并通过确定性完整性检查，才计入总体进度。

### Day 1 · 定义战场（100 分钟）

- **预算**：输入 25 分钟；实践 55 分钟；记录与验收 20 分钟。
- **目标**：把真实业务问题定义成可测量的 LLM 系统问题，明确系统边界、成功指标和退出条件。
- **核心材料**：李宏毅 Introduction to Generative AI，只看导论中的能力、应用形态与限制；NIST AI RMF 1.0，只读 Govern、Map 概览。
- **实践与产出**：画出数据、模型、检索/工具、推理、评测、运营链路，固定模型/数据/环境；提交 README、控制面/数据面架构图和质量、P95、成本、可用性指标表。
- **验收**：三道回答可复核；四类指标都有数据来源、测量方法、目标与退出或降级条件。浏览器只检查提交完整性，外部文件仍需学习者诚实声明或人工复核。

### Day 2 · 模型边界与 Transformer 机制（105 分钟）

- **预算**：输入 25 分钟；实践 55 分钟；记录与验收 25 分钟。
- **目标**：区分生成、推理、Embedding 与 Reranker 的职责，并用实验解释 token、embedding、causal attention 对质量、上下文、延迟和成本的影响。
- **核心材料**：Hugging Face LLM Course 的 Tokenizers 小节，只读 tokenization pipeline、subword 与 special token；《Attention Is All You Need》3.2.1、3.2.2 与 Figure 1；PyTorch `Embedding` 文档的输入/输出 shape 和参数定义。
- **实践**：统计 Day 1 的 20 条文本 token 分布并固定 tokenizer/版本；写模型能力矩阵；实现 embedding 与单头 causal attention，打印 Q/K/V、score、mask 和输出 shape，用断言证明未来 token 权重为零；手算 n=4/8 的 score 元素数与输入费用。
- **产出**：`model-boundary.md`、`token-stats.csv`、`attention_shapes.py`、`mechanism-note.md`。
- **验收与问题**：解释为什么生成模型不能替代 Embedding/Reranker；说明 token 对上下文、费用、延迟的影响及依赖条件；写出 attention shape，并区分 prefill score 的 O(n²) 与 KV Cache 容量随缓存 token 近似线性增长。证据需定位样本统计、版本、mask 断言和手算。回答必须包含收益、代价、约束和生产边界。
- **参考依据**：模型职责、指标与成本曲线不同；token 数依赖 tokenizer；标准 dense self-attention 建立 n×n score，decode 通过缓存历史 K/V 避免重复投影，但结论仍受模型结构、实现、硬件和计费口径限制。

### Day 3 · 最小 Transformer 实现（110 分钟）

- **预算**：输入 20 分钟；实践 65 分钟；记录与验收 25 分钟。
- **目标**：用最小可运行实现验证 decoder-only Transformer 的前向、训练与自回归生成路径，而不是追求训练大模型。
- **核心材料**：Karpathy `microgpt` 单文件实现，只读 tokenizer、参数、attention、loss、反向传播与生成段；PyTorch `CrossEntropyLoss` 文档，只看 logits/target shape 和未归一化 logits 约束。
- **实践**：固定小于 10 KB 的文本、seed 与配置；实现 token/位置表示、causal attention、MLP、residual、normalization 和 LM head；先过拟合单 batch，再运行至少 100 step；保存起止 loss、耗时或 tokens/s、生成样例；注入一次 mask 或 target 故障并修复。
- **产出**：`minimal_transformer.py`、`run-log.md`、loss 记录、生成样例和故障修复记录。
- **验收与问题**：解释 teacher forcing 训练与自回归推理在梯度、计算复用和性能代价上的差别；用断言/故障证据说明 causal mask；说明单 batch 过拟合的诊断价值、loss 不降的排查顺序及该实现的生产限制。固定 seed 命令可重跑，shape 断言通过，至少 100 step 且 loss 明显下降。
- **参考依据**：训练并行计算 next-token loss 并保留激活反传；推理逐 token 生成且可复用 KV Cache。过拟合单 batch 只能验证数据、target、前向、梯度和优化器闭环，不能证明泛化或生产可用性。

### Day 4 · 可追溯数据资产（105 分钟）

- **预算**：输入 25 分钟；实践 55 分钟；记录与验收 25 分钟。
- **目标**：把业务文档转成可重跑、可审计、可回滚的 chunk 数据集，并在发布前阻断 ACL 或血缘不完整的数据。
- **核心材料**：Hugging Face Datasets 的 `map/filter`、fingerprint 与 save/load；NIST AI RMF 的 MAP 3、MEASURE 2 数据条目；Azure AI Search 文档级访问控制中的 security filter 模式。
- **实践**：处理 10–20 份固定 Markdown/HTML 文档；记录 source/content hash、source/parser version、tenant、ACL、更新时间和 parent；规范化、精确去重、语义切分；重复运行并比较 manifest；报告重复/失败/缺失 ACL 比例；抽检 10 个 chunk 血缘；注入一个无 ACL 样本验证发布失败并设计回滚。
- **产出**：可重复脚本、versioned manifest、10 条血缘抽检、质量报告和涵盖 ACL 门禁、增量更新、下线与回滚的数据 ADR。
- **验收与问题**：两次运行 manifest hash 与 chunk 数一致；所有质量比例有分母；10/10 chunk 可追溯；无 ACL 样本被拒绝。回答需区分清洗、去重、metadata、版本与血缘的收益和代价，解释 chunk 的语义/召回/token/追溯取舍，以及 ACL 发布门禁、查询时强制过滤、审计和回滚闭环。
- **参考依据**：metadata 支持过滤与解释，版本支持复现，血缘连接 chunk 与原文/处理器；ACL 仅写入 metadata 并不安全，必须在发布和每次检索时按调用者身份强制执行。

### Day 5 · RAG 检索基线（100 分钟）

- **预算**：权威输入 25 分钟；基线实验 55 分钟；记录与验收 20 分钟。
- **目标**：在同一 query 集、语料/索引版本与运行环境下比较 BM25 和 dense retrieval，区分召回覆盖与排序问题。
- **核心材料**：RAG 原论文的摘要、方法 2.1–2.2 与实验设置；Sentence Transformers 官方 Semantic Search 文档的 symmetric/asymmetric search 与 retrieve-and-rerank；Elasticsearch 官方 BM25 similarity 参数说明。
- **实践与产出**：冻结至少 100 条带相关证据标注的 query；固定参数、模型版本、top-k、硬件、命令和随机种子；保存逐 query 排序及原始耗时；报告 recall@5/10/20、MRR、P50/P95、索引大小和构建时间，并分类至少 10 条失败记录。
- **验收与问题**：解释 BM25 与 dense 各自优势、recall@k 与 MRR 的区别，以及召回失败的排查顺序。证据摘要需定位可复现配置、命令、原始结果，并包含样本量、环境/版本、两类基线、质量指标、P95 和四类失败。
- **参考依据与衔接**：只有固定数据、配置和环境的对照结果才支持归因；Day 5 最佳配置成为 Day 6 唯一基线，失败 query 集不得改写。

### Day 6 · RAG 单变量消融与引用验证（100 分钟）

- **预算**：权威输入 25 分钟；消融与抽检 55 分钟；记录与验收 20 分钟。
- **目标**：一次只改变一个 RAG 变量，验证质量收益是否覆盖延迟与成本代价，并人工核对引用是否真正支持答案。
- **核心材料**：Ragas 官方 Metrics 概念文档中的 context precision/recall 与 faithfulness；LlamaIndex 官方 Evaluating RAG 文档中的 retrieval/response evaluation；RAG 原论文实验与 ablation。
- **实践与产出**：锁定 Day 5 的 query、索引、模型、prompt、top-k、随机种子和环境；从 chunking、hybrid、reranker、query rewrite 中选择变量，每个 run 只改一个；形成至少三组消融、20 条人工引用核验记录和串联 query、证据、prompt、答案、引用的 trace。
- **验收与问题**：解释各变量改变的环节、groundedness 的人工校准方法，以及“有引用”与“引用支持答案”的区别。每组实验需有 run ID、唯一变量和基线，并报告质量、P95 与成本差值。
- **参考依据与衔接**：没有固定基线或同时改变多个变量就不能归因；净收益最明确的配置进入 Day 7，未胜出方案成为否决候选。

### Day 7 · 第一周 go/no-go 架构评审（100 分钟）

- **预算**：权威输入 20 分钟；评审与决策 60 分钟；记录与验收 20 分钟。
- **目标**：综合基线、消融与失败样例，对 RAG v1 作出可审计的 go/no-go 决策，把最大未验证假设转成下一项实验。
- **核心材料**：Google Cloud Architecture Framework 官方 ADR 指南中的 context、options、decision、consequences；Full Stack Deep Learning 官方 Testing and Experimentation 课程中的错误分析与实验迭代。
- **实践与产出**：冻结评审包及样本量、版本、统计口径；用同一表格呈现质量、失败分类、P95 和单位 query 成本并对照阈值；产出第一周 ADR、RAG v1 决策表、至少一个有证据的被否决方案和下一项实验卡。
- **验收与问题**：必须明确 go/no-go，并解释 Prompt、RAG、SFT 与换模型的选择依据以及当前最大瓶颈。下一实验须写清假设、唯一变量、控制项、指标、成功阈值和停止条件；仅勾选完成声明不能通过。

## 14 天主线：Day 8–10 推理性能与受控服务

这一段承接 Day 7 的 go/no-go 评审。三天复用同一模型、硬件、runtime、请求样本和统计脚本，先建立基线，再用单变量实验解释 KV Cache 与调度，最后评估一种后端真实支持的量化格式。任何结论都必须写成“在什么环境和负载下观察到什么”，不能把局部 benchmark 泛化成普遍规律。

三天共用的最小证据字段：模型名称与 revision、GPU 型号/数量/显存和驱动、runtime 与版本、量化格式（未量化也要写 BF16/FP16）、采样参数、输入/输出 token 分布、并发或到达率、warm-up、成功/失败样本量、超时是否计入、percentile 算法，以及原始逐请求数据位置。少于 30 个成功请求只能作为冒烟结果；时间允许时延伸到 100 个以上，但延伸任务不影响当天最低通过。

### Day 8 · 推理性能基线（100 分钟）

**学习目标**：建立可复现的请求生命周期基线，分别解释排队、prefill、decode 与冷启动，避免用单个平均延迟代表服务性能。

**时间预算**：权威输入 25 分钟；最小实验 55 分钟；记录与验收 20 分钟。

**核心材料**：

- [vLLM Benchmark CLI](https://docs.vllm.ai/en/latest/cli/bench/serve.html)：只读请求率、输入/输出长度和结果字段，确认 TTFT、TPOT、ITL、吞吐的统计口径。
- [vLLM Metrics](https://docs.vllm.ai/en/latest/design/metrics.html)：只读队列、prefill/decode 和 KV cache 指标，把客户端耗时拆回服务端阶段。
- [NVIDIA GenAI-Perf](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/perf_analyzer/genai-perf/README.html)：只读长度分布、并发和 percentile 报告方法。

**实践**：

1. 用 10 分钟固定环境字段和 sampling 参数。
2. 用 15 分钟从真实样本或可解释的合成数据得到输入/输出 token 的 P50/P95，固定并发或到达率与 warm-up。
3. 用 30 分钟在 warm-up 后运行至少 30 个成功请求，保存逐请求时间戳；延伸实验再增加到 100 个请求和一个并发档位。
4. 用 20 分钟计算 TTFT、TPOT、E2E、队列等待的 P50/P95/P99，以及 request/token throughput；注明失败与超时如何进入分母。
5. 用 25 分钟画出排队 → prefill → 首 token → decode 生命周期，解释尾延迟并写明结论适用边界。

**产出与通过标准**：提交 benchmark 命令、原始数据、环境/负载清单、生命周期图和 percentile 报告。能解释 TTFT、TPOT、E2E 的起止点，说明 P95 与均值冲突时的排查路径；摘要字段齐全且不把当前结果推广到其他模型、GPU、runtime、量化格式或负载。

**检验问题与答案依据**：

1. TTFT、TPOT 与 E2E 分别如何计算？依据：TTFT 覆盖请求抵达、排队与 prefill 至首 token；TPOT 描述首 token 后相邻输出 token 的平均生成间隔；E2E 到完整响应结束。
2. P95 高但均值正常时先查什么？依据：按输入/输出长度、排队时间、冷/热路径和并发分层，不能只看聚合均值。
3. 为什么结果不能直接外推？依据：模型、硬件、runtime、精度、长度分布、到达过程和并发都会改变瓶颈。

### Day 9 · KV Cache 与调度（105 分钟）

**学习目标**：把 KV Cache 容量与 continuous batching 放进真实排队系统，依据观测区分计算、显存带宽、调度和排队瓶颈，并设计背压与多租户公平性。

**时间预算**：权威输入 25 分钟；最小实验 55 分钟；记录与验收 25 分钟。

**核心材料**：

- [PagedAttention 原论文](https://arxiv.org/abs/2309.06180)：读摘要、§3–4 和实验限制，理解分页减少碎片但不消除 KV Cache。
- [vLLM Scheduler 源码文档](https://docs.vllm.ai/en/latest/api/vllm/v1/core/sched/scheduler.html)：追踪 waiting/running、token budget 和 KV cache 分配。
- [vLLM Production Metrics](https://docs.vllm.ai/en/latest/design/metrics.html)：只看 cache usage、waiting requests、queue time、preemption 和 rejection。

**实践**：

1. 用 10 分钟引用 Day 8 环境，并补充 KV dtype、block/page 配置和可用显存。
2. 用 15 分钟估算每 token KV bytes：`2 × 层数 × KV heads × head_dim × dtype bytes`；GQA/MQA 使用 KV heads，不误用 attention heads，并注明实现开销。
3. 用 30 分钟完成至少 30 个请求的单变量实验：固定长度分布，只改变并发或长上下文占比；采集 cache usage、running/waiting、preemption/rejection、TTFT/TPOT/E2E P95。
4. 用 25 分钟把证据归到计算、显存带宽、调度或排队；没有 profiler/日志支持时写“未证实”。
5. 用 25 分钟为两个租户定义配额/权重、admission control、队列上限和 backpressure 响应，并分租户比较 P95、吞吐或拒绝率。

**产出与通过标准**：提交 KV Cache 容量表、单变量性能曲线、调度/队列 trace 和公平性 ADR。环境、负载、样本量、统计口径可复核；四类瓶颈明确区分；长上下文租户不能无边界挤占 cache，过载必须通过 admission control 和背压变成可观测拒绝。

**检验问题与答案依据**：

1. KV Cache 容量由什么决定？依据：层数、KV heads、head dimension、K/V 两份、dtype bytes、序列长度和并发；实现还可能有元数据和碎片。
2. continuous batching 的收益与代价是什么？依据：在 decode 迭代边界移入/移出请求提高利用率，但等待、抢占和大请求可能扩大 TTFT 与尾延迟。
3. 如何保护多租户？依据：admission control 限制可接受工作量，配额/权重决定资源份额，队列上限和 backpressure 快速拒绝或降级，并按租户观测 SLO。

### Day 10 · 量化与受控服务（110 分钟）

**学习目标**：在后端支持矩阵内验证一种量化方案，并把质量、显存、吞吐、P95 和成本证据接入可流式、可取消、可限流、可降级的服务路径。

**时间预算**：权威输入 25 分钟；最小实验 60 分钟；记录与验收 25 分钟。

**核心材料**：

- [vLLM Quantization](https://docs.vllm.ai/en/latest/features/quantization/)：先查硬件与方法兼容矩阵，只选择当前 runtime 明确支持且实际能加载的格式。
- [AWQ 原论文](https://arxiv.org/abs/2306.00978)：读方法与实验设置，理解 weight-only 量化的假设，不外推论文硬件结果。
- [vLLM OpenAI-compatible Server](https://docs.vllm.ai/en/latest/serving/openai_compatible_server.html)：只读流式、服务参数和接口，再由网关实现超时、取消、限流、幂等与 fallback。

**实践**：

1. 用 10 分钟确认一种后端支持的格式，例如 AWQ W4A16；记录模型/revision、GPU、驱动、runtime/version 和 kernel。不支持时提交阻断证据，不伪造数据。
2. 用 20 分钟以 Day 8 的同一输入/输出分布、并发、sampling 参数和至少 30 个请求，对比未量化基线与量化候选。
3. 用 20 分钟在固定 golden set 上，以预注册阈值比较任务质量和失败样例；同时记录权重/峰值显存、吞吐、P95 与单位请求或每百万输出 token 成本。
4. 用 20 分钟验证流式首 token、客户端取消、deadline/超时和限流；为可重试请求设置幂等键，有副作用的请求不得盲目重试。
5. 用 20 分钟定义超载或模型失败时的 fallback、熔断、恢复与回滚门槛，给出采用/拒绝/继续实验的条件化结论。

**产出与通过标准**：提交量化支持证据、同负载对照表、golden set 质量差异和失败样例、受控服务时序图。质量、显存、吞吐、P95、成本均注明样本量和统计口径。结论必须绑定当前模型、GPU、runtime、kernel、格式与负载，不能写“INT4 一定更快”。

**检验问题与答案依据**：

1. 为什么相同位宽不保证相同吞吐或 P95？依据：kernel、反量化开销、batch、KV Cache、调度与硬件支持会改变端到端瓶颈。
2. 如何决定质量退化可接受？依据：固定任务、golden set、解码参数和指标，预注册阈值并审查失败样例，而非只比平均自动分。
3. 受控服务如何处理超时与取消？依据：网关传播 deadline/cancel，后端停止无用生成，限流器在过载前背压；fallback 受质量、成本、数据边界和幂等约束。


## 14 天正式计划：Day 11–13

以下三天承接推理与服务基线，形成“质量校准 → 风险与成本判断 → 可恢复生产架构”的连续路径。每一天的外部产物由学习者诚实声明并保留人工复核；页面只做确定性的完整性检查，不声称自动证明实验结果。

### Day 11 · 评测与可观测性（100 分钟）

- **时间预算**：权威输入 25 分钟；实践 50 分钟；记录与验收 25 分钟。
- **核心材料与范围**：OpenAI Evals README（评测结构、数据与结果）；Ragas Metrics（groundedness/faithfulness 与检索指标及边界）；OpenTelemetry Traces（span、attribute 与 sampling）。
- **实践**：固定 100 条带 ID、版本和期望证据的 regression set；为任务成功率、groundedness、引用正确率和工具成功率写判定规则与阈值；自动评测后按固定方法人工抽检至少 20 条，记录分歧类型与处理结论；定义覆盖检索、prompt、模型、工具和回答的 trace schema，对 PII、密钥与正文删除、哈希或掩码，并区分正常、错误、慢请求和安全事件的采样率与保留期。
- **可观察产出**：固定评测集清单、指标规则表、至少 20 条人工校准记录、自动/人工差异报告、trace schema 与采样/脱敏策略。
- **通过标准**：明确 100 条固定样本和至少 20 条人工抽检；指标有规则与阈值；差异有归因；trace 有脱敏、采样率、保留期及错误优先策略。缺少样本量或人工校准不能通过。
- **检验问题**：自动评测为什么不能替代人工验收？trace 中哪些字段必须脱敏？如何控制 trace sampling 和高基数标签成本？
- **判断依据**：自动 judge 会随模型、提示词和样本分布偏移，必须用固定样本、标注规则与人工抽检校准；trace 只收集诊断所需字段，同时保留错误证据并控制隐私与成本。
- **延伸（不计入 100 分钟）**：扩大回归集、做标注者一致性分析，并把质量门禁接入 CI 或灰度发布。

### Day 12 · 安全、权限与成本（110 分钟）

- **时间预算**：权威输入 25 分钟；实践 60 分钟；记录与验收 25 分钟。
- **核心材料与范围**：OWASP Top 10 for LLM Applications（Prompt Injection、Sensitive Information Disclosure、Excessive Agency）；NIST AI RMF Measure/Manage（控制证据、责任人与残余风险）。
- **实践**：分别执行 prompt injection、越权检索、数据泄露、工具滥用攻击；记录输入、身份/ACL、目标资源、结果与日志/trace；登记预防、检测和响应控制、误报样本、影响范围、残余风险、风险余量与责任人；画出身份和 tenant/ACL 经网关、检索、工具逐跳传播的权限图；用公式重算请求量、输入/输出 token、检索、存储、GPU 与人工成本，并加入峰值 QPS 和故障余量。
- **可观察产出**：四类攻击证据表、控制/误报/残余风险登记、权限传播图、可按 QPS 和 token 分布重算的成本容量表。
- **通过标准**：四类攻击都有证据；权限在检索和工具层执行；控制同时报告拦截与误报；残余风险和风险余量明确；成本公式含假设、单位、峰值与容量余量。缺少权限证据、残余风险或可重算参数不能通过。
- **检验问题**：Prompt Injection 与越权检索有什么区别？工具调用为何必须传递用户权限？如何计算单位任务成本与峰值容量？
- **判断依据**：内容操纵与授权绕过是不同风险；安全不能只依赖 prompt。工具应使用调用者身份、最小权限、参数校验和副作用审批；成本容量来自请求量、token 分布、资源单价、峰值和故障余量。
- **延伸（不计入 110 分钟）**：扩展至供应链、拒绝服务和日志泄露，由安全团队独立红队复核。

### Day 13 · 生产架构与故障演练（100 分钟）

- **时间预算**：权威输入 20 分钟；实践 55 分钟；记录与验收 25 分钟。
- **核心材料与范围**：Google SRE Workbook 的 Non-Abstract Large System Design（容量与故障权衡）；AWS Builders Library 的 Avoiding overload（backpressure 与重试边界）；KServe 控制面文档（部署、路由和在线请求职责）。
- **实践**：画出控制面/数据面、区域和依赖故障域，标注多租户配额、公平调度、admission control、backpressure 与容量余量；为模型不可用、检索超时和写入失败定义 fallback、熔断和降级；用幂等键与去重记录保护副作用；为配置、索引和会话状态定义 RPO/RTO、复制、切换与回退；执行一次演练并记录注入、告警、切换、数据核对、恢复时间和改进项。
- **可观察产出**：生产架构图、SLO/配额表、故障时序图、RPO/RTO 表和带时间戳、指标与数据核对的演练复盘。
- **通过标准**：控制面/数据面与故障域明确；包含配额、公平性、backpressure、fallback、幂等和容量余量；RPO/RTO 可测且有恢复证据。只写“重试”不能通过。
- **检验问题**：控制面与数据面分别承载什么？active-passive 的 RPO/RTO 如何定义？消息重放和重试如何避免重复副作用？
- **判断依据**：过载先通过 admission control/backpressure 控制进入系统的工作，再按业务语义 fallback；盲目重试会放大故障。RPO 衡量可接受数据丢失，RTO 衡量恢复时长，必须由演练时间戳、指标和数据核对证明。
- **延伸（不计入 100 分钟）**：在隔离测试环境执行真实区域切换、混沌注入和消息重放。

## 14 天正式计划：Day 14 发布答辩

### Day 14 · 架构答辩与 90 天路线（110 分钟）

- **时间预算**：证据组装 25 分钟；答辩与质询 55 分钟；记录与验收 30 分钟。
- **目标**：把前 13 天的产出压缩成可质询的架构决策，证明每个关键决定有数据、实验或风险证据，并明确未知与退出条件。
- **核心材料与范围**：Google Cloud Architecture Framework 的 ADR 指南（context、options、decision、consequences）；Google SRE Workbook 的 Non-Abstract Large System Design（需求、容量、冗余与故障）；NIST AI RMF 的 Govern、Measure、Manage（责任、测量、残余风险与处置）。
- **实践**：建立证据索引；从峰值 QPS、输入/输出 token 分布、服务时间、KV Cache、实测单卡容量和故障余量推导副本及成本；准备覆盖模型/runtime 选型、质量归因、身份/tenant/ACL、安全攻击、降级、恢复、RPO/RTO、灰度、回滚和退出条件的答辩；列出至少 5 个 trade-off 与 3 个 unknown；按价值、风险、依赖和可逆性排列 30/60/90 天优先级，并为最高风险 unknown 设计下一步实验。
- **可观察产出**：10–15 页架构决策简报和证据索引、模型选型 ADR、容量/成本推导表、质量归因树、权限/威胁与恢复附录、退出条件、trade-off/unknown 清单，以及带实验门槛的 30/60/90 天路线图。
- **通过标准**：答辩覆盖模型选择、容量推导、质量归因、权限安全、故障恢复、成本、退出条件与 90 天优先级；每个关键决策引用 benchmark、指标或风险证据；至少 5 个 trade-off、3 个未验证假设和一个包含假设、唯一变量、控制项、样本量、成功阈值、停止条件、负责人的下一步实验。自动检查只确认结构与必要证据词，外部产物必须由资深架构师人工复核。
- **检验问题与答案依据**：
  1. 为什么选择当前模型与 serving runtime？依据：真实业务质量、延迟、成本、许可证和数据边界，并说明备选、trade-off 与退出条件。
  2. 如何推导容量与成本，并定位质量下降？依据：到达率、token 分布、服务时间、KV Cache、实测单卡容量、目标利用率和故障余量；质量沿数据、检索、上下文、模型、工具的 trace 分层归因。
  3. 权限、安全、恢复与路线如何答辩？依据：调用者身份和 ACL 在检索/工具服务端逐跳执行；攻击、误报和残余风险有记录；降级、RPO/RTO、恢复和回滚有演练；30/60/90 天优先级由价值、风险、依赖与可逆性决定。
- **答辩后动作**：未达到退出条件或安全签署前不扩量。所有 unknown 保留为 unknown，直到预注册阈值的实验产生证据。

## 14 天发布验收

发布检查必须逐日覆盖 14 天，并由两个模拟角色从完整浏览器页面验收：

- **普通学习者**：能发现两周导航，理解每日目标、90–120 分钟预算、材料范围、实践、产出、通过标准和问题；能经历未开始、进行中、待验收、需补充、已通过，刷新后恢复并安全重置。
- **资深架构评审者**：逐日判断技术准确性、来源权威性、任务可执行性、产出可观察性、标准可判定性、问题/答案依据和前后衔接；重点质询 Day 7 的 go/no-go 证据和 Day 14 的端到端答辩。
- **进度门槛**：总体百分比只统计 `已通过`。只有 14 天全部通过才显示 100%；任一天处于其他状态都不得宣称整体完成。
- **链接与无障碍**：核心链接必须指向声明的官方文档、原论文或源码，并具备安全的新窗口属性；在线探测无法执行时报告环境限制，不把未探测当作可访问。对话框有名称并返回焦点，状态可播报，键盘可完成关键流程。

内容审计记录以浏览器回归测试为可执行基线。它检查每一天的完整字段和足够具体的工程证据词，而不是仅判断节点存在；真实实验数据、链接长期可用性和人工签署仍属于明确的人类复核边界。

## 架构师级最终能力

完成规划后，应能独立回答以下问题：

1. 为什么这个问题应该用 RAG，而不是 SFT 或换模型？
2. 在给定上下文、并发和 SLO 下，需要多少 GPU，单请求成本是多少？
3. 质量下降时，如何区分数据、检索、上下文、模型和工具问题？
4. 模型、提示词、索引和评测集如何版本化、灰度和回滚？
5. 如何保证多租户权限不会通过检索或工具调用泄露？
6. 自建模型与外部 API 的边界如何划分？
7. 一个 Agent 失败后，如何恢复、审计、限损并避免重复副作用？
8. 这个项目在什么指标下继续投入，什么条件下停止？

最终应留下四类资产：模型选型矩阵、平台参考架构、可复现实验/容量模型、一个真实业务的端到端落地方案。
